# Phase 1B: farmer-to-market integration

Status: **implemented locally, committed locally, not deployed, pushed or merged.** A hardening pass follows in the last section (items marked there supersede earlier text). Stack unchanged: React, TypeScript, Node.js, SQLite. Builds on Phase 1A (crop check and advice cards) and extends the **existing** marketplace, offline sync, idempotency and Ministry modules instead of replacing them. No payments, SMS, USSD, voice recordings or external AI were added.

## 1. What was added
| # | Request | What exists now |
|---|---|---|
| 1 | Harvest listings | `POST /marketplace/listings` accepts `cropSlug`, `quantityKg`, `harvestDate` (price, county, town, description, phone and status as before). The server validates crop, **whole kilograms 1 to 1 000 000** and a **real harvest date** (not in the future, not older than 400 days) and **derives** category, product name, quantity and unit from them. Plain listings (no `cropSlug`) are unchanged. Ownership, moderation and the Phase 0 limits are reused. Status (`Available`, `Limited Stock`, `Sold Out`) and ownership (owner device key or account, administrator) use the existing edit route; the crop cannot be changed. |
| 2 | Offline listings | "Sell my harvest" saves the listing on the phone first (existing drafts store), queues it, and the existing sync engine sends it with the **same `Idempotency-Key`** on every retry. A lost response or a retry returns the stored result: one row, one reference. Back-off and `Retry-After` handling are the existing ones. |
| 3 | Tracking codes | `SELL-YYYY-NNNNNN` is **issued by the server** from the unique row id when the listing is created (so after the first successful sync), shown on the farmer's listing ("Reference: the server will issue it after this reaches it" until then), and never generated in the browser. Every listing, old or new, has one. The screens say it is **a lookup number, not a blockchain, not a signature and not proof of origin or quality.** |
| 4 | Buyer discovery | `/harvest`: filters (crop, county, minimum kg, maximum price per kg, status, show sold out). The full list is saved on the phone with the time it was saved; offline it is shown as **"Saved list from <time>. It may be out of date"**, filters still work (they run on the phone and are tested to equal the server's), and a reference can be checked against the saved list (labelled as such). A seller's phone number appears **only if the seller consented**. |
| 5 | Buyer inquiries | The existing inquiry route is extended: **idempotent retries**, the buyer's private device key (stored only as a keyed hash) and an explicit consent flag for sharing the buyer's phone; a hidden or flagged listing answers exactly like a missing one. New `GET /harvest/inquiries` returns **only conversations the caller is part of**: the seller (owner account, or the device holding the listing key) sees buyer name, county and message, and the buyer's phone **only with the buyer's consent**; the buyer (device key or account) sees their own questions and the seller's replies. Everyone else gets an empty list. Raw rows (buyer token, user ids, key hashes) are never returned. Replies use the existing owner-only route. Phase 0 limits and the synthetic-only demo phone policy apply unchanged. |
| 6 | Ministry analytics | `GET /insights/aggregates` and a new "Harvest and crop checks (privacy-protected)" section on `/ministry-analytics`: harvest listings by county and by crop (listings, farmers, total kg, average price per kg) and crop checks by crop and by county (checks, devices, Green/Yellow/Red). **A group is published only with at least 3 records from at least 3 different farmers or devices**; smaller groups are merged into one "Other" row so tables always add up (a table that just dropped small groups would let a reader subtract one table from another). If the merged row is itself too small, the smallest published group is folded in; if everything together is too small, nothing is shown. No names, phone numbers, towns, reference codes, dates of single records or photos. The page and the response are labelled **"SIMULATED DEMONSTRATION. This is not an official Ministry system and these are not official statistics."** Offline it shows a labelled saved copy. |
| 7 | Complete demonstration | `/demo/farm-to-market` (twelve steps, each tagged Working / Simulated / Draft) and the walkthrough below. Synthetic background data: `ENABLE_DEMO_MARKET_DATA=1` or an administrator's button (`POST /admin/demo/market-data`); never in production. |

## 2. Screens and routes
Pages: `/harvest/sell` (farmer), `/harvest` (buyer), `/demo/farm-to-market` (presenter), new section on `/ministry-analytics`. Home lists the first two under Farm Tools.
API (all under `/api/v1`): `GET /harvest/listings`, `GET /harvest/listings/:code`, `GET /harvest/verify/:code` (60 per 10 minutes, one identical 404 for every unknown, malformed, hidden or non-harvest reference), `GET /harvest/inquiries`, `GET /insights/aggregates` (120 per minute), `POST /admin/demo/market-data` (administrator, not in production). Extended: `POST` and `PATCH /marketplace/listings`, `POST /marketplace/listings/:id/inquiries`.
Migration `010_harvest_market` (additive, with a down file; the down file discards harvest fields, codes, buyer keys and consent flags, so back up first): listing code, crop, kilograms, harvest date and harvest flag on listings; buyer key hash and phone-consent flag on inquiries; synthetic marker on crop-check reports; a unique index on the code.

## 3. Privacy and safety summary
* Seller phone: consent only (existing rule). Buyer phone: consent only (new). Demo environment: synthetic numbers only (Phase 0 rule) for sellers **and** buyers.
* Conversations: only the two parties; sellers prove ownership with the listing's private key or account, buyers with their private device key or account.
* Aggregates: counts and totals only, k = 3 records and 3 contributors, merged "Other" row, no cross-tab, no grand total; computed from approved harvest listings and crop-check reports; labelled simulated; synthetic records are marked and the panel says when they are included.
* Existing responses keep their exact shape: the harvest block appears only on harvest listings, and the contract golden is unchanged.
* This is k-anonymity style protection for a demonstration, **not** a formal privacy guarantee.

## 4. Presenter walkthrough (about 8 minutes)
Preparation: start the demonstration server with `ENABLE_DEMO_MARKET_DATA=1` (or sign in as the administrator and press "Load synthetic market data" on `/demo/farm-to-market`). Use two browser profiles: Farmer and Buyer. Synthetic accounts and numbers only (+23177000xxxx).
1. **Farmer** opens **Check my crop**, chooses Cassava, "young leaves patchy or twisted", answers, ticks "add my result to the anonymous county counts", sees a Yellow result and advice card `ADV-2026-001` labelled *NOT reviewed by a qualified agronomist*.
2. Switch the phone to **airplane mode**. Open the saved check and the advice card: both open ("Saved copy on this phone").
3. Still offline, open **Sell my harvest**: cassava, 500 kg, price, county, harvest date. It shows **Pending Sync** and "the server will issue the reference".
4. Reconnect. The listing is sent by itself and shows its **SELL reference**. (Pull the plug mid-send if you like: a retry never creates a second listing.)
5. **Buyer** opens **Find harvest**, filters by crop and county, sees the listing (and the synthetic ones), no seller phone because the seller did not agree.
6. Buyer goes offline: the list opens with "Saved list from <time>, may be out of date"; filters work; the reference check says it found it in the saved list only.
7. Buyer reconnects, asks the seller a question.
8. **Farmer** sees the question under the listing and replies. **Buyer** sees the reply under "My questions". A third profile sees neither.
9. Open **Ministry & Extension View**: the harvest and crop-check tables include the new listing and check; groups under 3 are merged into "Other"; the banner says it is simulated and not an official Ministry system.

## 6. Known limitations
1. **Inquiries need a connection** (no offline inquiry queue); the buyer's list of questions is not saved for offline reading.
2. **Buyers have no accounts**: a buyer is a device key (or a signed-in account). Two roles in one browser share that browser's keys; use two profiles.
3. The **legacy** `GET /marketplace/inquiries` still returns raw rows (including the buyer's client token and user id) to the listing's owner. Its shape is pinned by the contract golden; the new screens use the whitelisted `/harvest/inquiries`. Tightening it needs an approved golden update.
4. Aggregates are **public** (counts only) and a demonstration-grade k = 3 suppression, not a formal guarantee; with very few real contributors the numbers are mostly synthetic and are labelled as such.
5. `ENABLE_DEMO_MARKET_DATA` reloads the synthetic rows at every start (it also removes inquiries made on synthetic listings).
6. Harvest listings have **no photo**; the crop cannot be changed after creating (create a new listing); a listing already on the server cannot be deleted from the phone (it can be marked Sold Out).
7. Prices are a single price per kilogram in LRD; no currency conversion, delivery or payment.
8. Not verified: real devices, screen readers, slow networks, the Hostinger runtime, the PHP `test:m3`.

## 8. Hardening pass (after the first Phase 1B commit)
1. **Legacy inquiry routes.** `GET /marketplace/inquiries`, the response of `POST /marketplace/listings/:id/inquiries` and the owner's reply response of `PATCH /marketplace/inquiries/:id` returned raw rows (buyer client token, user ids, key hash; the PATCH reply even handed the seller the buyer's phone without consent). They now use one explicit allow-list (`server/inquiryView.ts`): names, county, message, reply, status, dates and listing summary; the buyer's phone only if the buyer consented (a buyer always sees their own). The contract golden pins only the anonymous empty list for this route, so **no golden entry needed changing**; the shape is pinned in `tests/hardening.test.ts`.
2. **Demonstration data is safe to repeat.** Migration `011_demo_seed_keys` gives every synthetic record a stable key. Start-up and the admin button only **add what is missing**; questions, replies, status changes and view counts survive restarts. Earlier-seeded rows adopt keys in order (no duplicates). A full reset is a separate, confirmed administrator action (`{reset: true}`) that deletes only synthetic rows (and their questions). Production refusals are unchanged and tested.
3. **Conversation authorization.** Reviewed and tested: seller (account or listing key) and buyer (account or device key) see only their own conversations; keys do not work in the other role or for another listing; a seller cannot answer another listing's question; hidden listings return the same 404 as missing ones for new questions, **close seller replies** (an administrator can still answer), and stay invisible to outsiders. New: guessable device keys (fewer than 10 different characters, e.g. `aaaa...`) are refused for harvest listing keys and buyer keys, because anyone could guess them and read a conversation. The app's own 256-bit keys are unaffected.
4. **Ministry aggregates.** Real entries and synthetic records are now **two separate blocks** (no combined figures to difference against), each suppressed on its own (3 records and 3 farmers or devices). Query parameters (filters, paging) are ignored, there are no totals, the number of merged groups is no longer published, kilogram totals are rounded to 50 and prices to L$ 5, and each block changes only after at least 3 records were added or removed (`INSIGHTS_MIN_CHANGE`, default 3; below 3 refused in production and the demo environment), so one person's single entry cannot be found by comparing two visits. 2000 random datasets check the suppression invariants.
5. **Tests.** `tests/hardening.test.ts` (11, `npm run test:hardening`); `tests/harvest.test.ts` and `tests/harvest-client.test.ts` updated for the new aggregate shape. Removing any of three fixes (raw reply row, reset on start, batching) makes the new tests fail (checked by hand).

Presenter note for step 9: a farmer's own entries appear in "Contributions entered through this app" only once a group has 3 different farmers or devices, and then only after the next batch; the synthetic statistics are always shown separately and labelled invented.

### Remaining risks
* Legacy `ownerKey` and device keys accepted before this pass (any 32 to 128 character string) still work for older features; only harvest listings and buyer inquiries require random-looking keys.
* Complementary suppression can un-fold a group when one record is added; batching reduces but does not remove this, and a person who adds two records themselves can still infer a third. This is k-anonymity style protection, not a formal guarantee; harvest listings are also public one by one in buyer discovery, so their aggregates protect little by themselves.
* A non-owner PATCH on an existing inquiry answers 403 and on a missing one 404 (an inquiry id can be probed); pinned by an older API test.
* No per-listing cap on questions (the per-address hourly limit applies).
* A migration (011) will be applied to a developer's existing database at the next start of the server; take a copy first if the data matters.
